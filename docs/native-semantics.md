# Native semantics evidence

## Hillstone

The [StoneOS 5.5R8 E-Pro guide](https://www.hillstonenet.com/wp-content/uploads/StoneOS_WebUI_User_Guide_E-Pro.pdf), printed pages 29–31, places BNAT before ordinary NAT in each direction, destination selection before routing and source selection after routing. Address rewriting occurs after session establishment. The implementation infers original-packet selection for the combined pipeline from that delayed rewrite sequence and enables mixed regular chains only for the explicit `5.5R8` software family. A real-device trace is still needed to validate interoperability; other version families remain unsupported for mixed evaluation.

The [5.5R5 CLI guide](https://kb.hillstonenet.com/en/wp-content/uploads/2017/11/StoneOS_CLI_User_Guide_Complete_Book_5.5R5-1.pdf), NAT chapter, identifies `static`, `dynamicip` and `dynamicport` as separate SNAT modes and defines BNAT as a bidirectional fixed mapping. Fixed SNAT is represented by `StaticNAT`; pool allocation remains `DynamicNAT`. This source does not establish mixed-chain behavior for 5.5R5.

Native SNAT and DNAT IDs have separate namespaces inside each VRF. Go catalog IDs retain VRF and chain (for example `trust-vr/snat:1`); `Object.Name` retains the device ID. BNAT's inverse is an execution reference to the same `StaticNAT`, not another persisted object. Multi-step results carry each selected reference in `NATRelation.Steps`.

Unsupported selectors, invalid references and unproven mappings consume potential traffic as unknown. Missing egress evidence cannot satisfy an `eif` selector. Each stage shares the evaluation visit budget.

## Junos SRX

The [Junos NAT overview](https://www.juniper.net/documentation/us/en/software/junos/nat/topics/topic-map/security-nat-overview.html) establishes rule-set selection before ordered rule matching. Interface, zone and routing-instance contexts have different priorities. The current implementation supports zone-only contexts and retains other contexts as pending. The processing order is static NAT, destination NAT, routing and policy, reverse static NAT, then source NAT. Policy sees the translated destination service. `QueryPacket` derives the destination zone through routing and only evaluates the source stage for permitted traffic; `QueryNAT` requires that destination-zone context from its caller.

The [static NAT guide](https://www.juniper.net/documentation/us/en/software/junos/nat/topics/topic-map/security-nat-static.html) establishes explicit bidirectional equal-size subnet mappings and paired destination/mapped port ranges. These are `StaticNAT` objects. The [destination NAT guide](https://www.juniper.net/documentation/us/en/software/junos/nat/topics/topic-map/security-nat-destination.html) distinguishes pool-based incoming translation and address/port forwarding. A single fixed destination pool is supported; larger pools retain unknown allocation semantics. They remain `DynamicNAT` objects with an explicit fixed destination relation, rather than becoming bidirectional static aliases.

The [source NAT guide](https://www.juniper.net/documentation/us/en/software/junos/nat/topics/topic-map/nat-security-source-and-source-pool.html) describes PAT by default, explicit `port no-translation`, and the 1024–65535 allocation range. Explicit pool ranges are retained. Results describe possible allocations, never observed session bindings. Source and destination pools have independent identities even when their native names match.

The [address-book guide](https://www.juniper.net/documentation/us/en/software/junos/security-policies/topics/topic-map/security-address-books-sets.html) gives attached books priority over global objects, then predefined names. Zone attachments participate in the sealed graph and semantic digest. Planning checks visibility before reusing an address; native readback compares policy order within each zone pair. Tests use synthetic display-set captures, not a live SRX or a complete Junos compatibility matrix.

## ScreenOS Netscreen

Juniper's [NAT migration application note](https://supportportal.juniper.net/sfc/servlet.shepherd/document/download/0693c00000LXgNrAAL?operationContext=S1) supplies native MIP, VIP, DIP, `fix-port`, interface source NAT and policy destination NAT examples. The Go parser retains MIP as `StaticNAT`; VIP and policy translation use `DynamicNAT`, and DIP remains a separate pool. Policy NAT references its owning security rule and is evaluated only for that rule's first-match permitted traffic. Earlier plain permits, denies and unknown rules cannot be skipped.

The [ScreenOS destination NAT guide](https://supportportal.juniper.net/sfc/servlet.shepherd/document/download/0693c00000LXgMAAA1?operationContext=S1), pages 1–2, requires routing for the original public address and keeps original/translated destination addresses in the same security zone. `QueryPacket` enforces both conditions. MIP/VIP instead resolve the real destination before route lookup; policy matching retains the original address and service view.

The Juniper-authored [ScreenOS 6.2 Concepts & Examples reference](https://sup.xenya.si/sup/info/Juniper/SSG/ScreenOS_V6.2.0/Concepts%20%26%20Examples%20ScreenOS%20Reference%20Guide%20-%20All%20volumes%20combined_ce_all.pdf) is available through this archived mirror. Volume 2, printed pages 11–12, 31 and 161–164 establish MIP/VIP route resolution, intrazone bypass without blocking, and the Untrust default exception. Volume 8, pages 2–3 and 63–64 establish PAT's reserved low ports, MIP/VIP priority over policy DNAT and bidirectional MIP mappings. Tests cover explicit intrazone block/unblock, original ports, PAT versus `fix-port`, and snapshot identity. Overlapping interface mappings and mixed interface/policy rewrites in opposite directions remain unknown; no live ScreenOS interoperability is claimed.

## FortiOS Fortinet

The [FortiOS policy guide](https://docs.fortinet.com/document/fortigate/7.4.0/administration-guide/656084/firewall-policy) distinguishes policies referencing VIPs from ordinary address policies. A deny policy with `match-vip` enabled participates in VIP lookup. The [best-practices guide](https://docs2.fortinet.com/document/fortigate/7.4.0/best-practices/862226/policies) dates the default change for new deny policies to 7.2.4. Explicit settings are retained; absent settings require a recognized captured software version. The immutable rule stores `MatchVIP`, and ambiguous defaults remain unknown during VIP evaluation.

The [VIP guide](https://docs.fortinet.com/document/fortigate/7.4.4/administration-guide/443514/configuring-vips) distinguishes the external policy interface from the mapped address and port. Fixed address VIPs are `StaticNAT`; port-forward VIPs are `DynamicNAT` with explicit address/port relations. Destination resolution precedes the packet route lookup. The [Fortinet port-forwarding technical note](https://community.fortinet.com/fortigate-3/technical-tip-configure-port-forwarding-using-fortigate-vips-98402) requires both external and mapped service ports when restricted. The current evaluator establishes results when the original and translated service matches agree; one-sided differences stay unknown instead of guessing across versions. VIP groups retain member identities rather than flattening into ordinary public addresses.

The [Fortinet source-VIP technical note](https://community.fortinet.com/t5/FortiGate/Technical-Tip-How-to-use-a-VIP-s-External-IP-Address-for-Source/ta-p/189947) specifies source-selection priority: forced VIP, policy IP pool, ordinary reverse VIP, then interface address. Source translation requires the selected security policy's NAT setting, and reverse VIP activation depends on an enabled referencing policy. Removing a shadowed policy can therefore change source translation; lifecycle equivalence checks the activation dependency. Address mapping and possible source-port allocation are reported separately. Port-forward source forcing remains unsupported.

The [default service source-port documentation](https://docs.fortinet.com/document/fortigate/6.2.0/new-features/466822/firewall-allow-to-customize-default-service) specifies 1–65535 and a global override. TCP/UDP custom terms retain each destination/source pair. The [static VIP guide](https://docs.fortinet.com/document/fortigate/7.2.7/administration-guide/510402/static-virtual-ips) describes source forcing and local-address side effects. A packet to an unresolved local VIP or pool address cannot be established by an ordinary route alone; `QueryPacket` retains unknown evidence there.

Native `config`/`edit` hierarchy is validated before targeted passes. Other VDOMs are explicitly ignored, unknown nested blocks stay pending, and interfaces precede route binding. Captures with explicit VDOM wrappers never assign stray global objects to the selected domain. Snapshot semantic format 6 retains the chosen `Metadata.Context`; command rendering requires callers to enter that VDOM. Tests are synthetic offline captures and independent readbacks. They do not establish live FortiGate interoperability or full native syntax coverage.

## Configuration persistence and capture

The StoneOS 5.5R5 CLI guide, printed page 372, distinguishes the saved startup configuration (`show configuration startup`) from the configuration in use (`show configuration running`). The adapter reads these separately. Save completion uses the connector profile's affirmative Hillstone response validation; a returned prompt alone is insufficient.

The [ASA 9.17 configuration guide](https://www.cisco.com/c/en/us/td/docs/security/asa/asa917/configuration/general/asa-917-general-config/intro-start.html) describes saving configuration with `write memory` and shows affirmative configuration-copy completion output. The adapter requires both the configuration-building response and `[OK]`; unknown formats remain unconfirmed. Its ASA profile and capture/restore workflow currently have synthetic transcript coverage.

The [PAN commit guide](https://docs.paloaltonetworks.com/ngfw/pan-os-cli-quick-start/use-the-cli/commit-configuration-changes) describes querying an exact job ID and inspecting finished job results. `Validate` and `Commit` are different jobs. The adapter accepts only a matching `Commit` row with `FIN OK`, validates its time columns and rejects ambiguous rows. Polls share one output budget and deadline.

The [PAN-OS 11.1 operational command hierarchy](https://docs.paloaltonetworks.com/pan-os/11-1/pan-os-cli-quick-start/cli-command-hierarchy/pan-os-11-1-cli-ops-command-hierarchy) includes `show config saved`. The [configuration backup guide](https://docs.paloaltonetworks.com/pan-os/11-1/pan-os-admin/firewall-administration/manage-configuration-backups/save-and-export-firewall-configurations) identifies `running-config.xml` as persistent running configuration, distinct from unsaved candidate changes. Recovery reads that saved file independently and requires complete XML before native parsing. These source-backed command choices do not establish real-device or every-firmware interoperability.

## Huawei

The current implementation follows the local Perl `Firewall::Config::Parser::Huawei` and Ruby `Algosec::Vendors::Huawei` parser, network syntax, service terms, NAT server/action and policy behavior. These are reference implementations, not independent proof of every USG version. Synthetic fixtures exercise V500R005-shaped configuration, separate NAT catalogs, original-packet NAT selection, post-DNAT route/service policy and source allocation only after permit.

Sections retain native indentation and `#` boundaries; unknown sections stay opaque. Interfaces and zone memberships precede static-route binding. A VPN rebind clears prior interface addresses. Object reopening preserves its first identity and replaces members by explicit index; mixed automatic/explicit indices remain unsupported. Service alternatives preserve their protocol, source-port and destination-port pairing. Native address and service values have explicit inline ownership, allowing lifecycle deletion without leaving a fictitious independently configured object behind.

Fixed server address mappings use `StaticNAT` with an explicit inverse when enabled. Protocol/port servers and complete `nat-policy` actions use `DynamicNAT`; pools retain their direction and identity. Server-map overlaps stay unknown. Protocol-specific reverse maps without `no-reverse` retain a global diagnostic because their possible effect includes traffic outside the forward match. NAT policy actions in both directions remain one selected declaration, and destination/bidirectional policy priority follows the Ruby reference. Mixed server-map and opposite-direction policy translation remains unknown pending stronger native evidence. Source pools and Easy-IP describe possible allocation, not session state.

The earlier Ruby capability notes cite the [Huawei NAT server command reference](https://info.support.huawei.com/hedex/api/pages/EDOC1100278054/AEL11217/08/resources/dc/nat_server.html). On 2026-10-28 this URL redirected to the support portal shell, and the connected web search service returned an authentication error. The command page was therefore **not reverified** in this implementation pass. Wider native/version verification remains open; successful synthetic tests are not a claim of live-device parity.
